# Architecture

MoniTopo separates portable decision-making from Windows integration and WPF presentation.

## Boundaries

- `MoniTopo.Core` owns persisted records, normalization, validation, matching, activation orchestration, and update state. It has no WPF or Win32 dependency.
- `MoniTopo.Windows` owns CCD, SetupAPI, hotkey, startup, session, and shell integration behind interfaces.
- `MoniTopo.App` owns WPF lifecycle, tray behavior, windows, view models, and user feedback.
- `MoniTopo.Recovery` is a small companion that can restore a transient rollback snapshot if the main process fails during activation.

WPF is used because MoniTopo is a compact Windows-only desktop utility that needs native input, DPI, theme, tray, and window behavior. GPU-vendor SDKs are excluded because saved profiles cover Windows display state rather than vendor-specific policy.

## Capture and persistence model

A profile stores only its desired active paths. Each path includes a composite monitor fingerprint, topology grouping, canonical position relative to the primary display, exact source and target signal data, refresh rational, orientation, path scaling, Windows UI scale, HDR state, and a friendly label. Inactive or disconnected displays are not profile requirements.

The configuration is a versioned JSON document under the user's local application-data directory. Writes go to a same-directory temporary file, flush to disk, and replace the current file while retaining one `.bak` file. Invalid documents are copied to a timestamped corruption file and left in place so a subsequent launch cannot silently reset them. Startup offers an explicit restore only when the backup also passes shape, migration, and domain validation. A missing primary with an existing backup takes the same recovery path. Configuration mutations run against the latest state inside one save gate; notifications run afterward, and observer failures cannot undo a committed save.

## Safety boundary

Core tests operate on immutable synthetic records. `DisplayMutationAuthorization` can be created only when the caller marks an explicit user/manual activation command and the inherited environment contains the exact value `MONITOPO_ALLOW_REAL_DISPLAY_CHANGES=1`. The production mutation facade has no unguarded constructor. Tests inject a fake environment reader and fake native API; CI has no display mutation command and never sets the opt-in.

## Windows capture

`CcdCaptureService` queries `QDC_ALL_PATHS` with virtual-mode and Windows 11 virtual-refresh awareness on a worker thread. Bounded retries handle changed buffers, temporarily unavailable active targets, and incomplete modes. A second topology observation checks that device-property reads belong to a coherent capture. Optional inactive-target names and preferred modes do not invalidate a complete active setup. Capture converts active source modes, exact target video signals, virtual desktop-image regions, and refresh-boost state, identifies the primary GDI source, records clone groups, and separately enumerates connected inactive targets. Some Windows 11 display stacks return packed virtual-aware indices while omitting the path's virtual-mode capability flag. MoniTopo therefore validates both the direct and packed candidates against the mode-array type, adapter, and source/target ID instead of treating the flag as the sole discriminator. Microsoft documents that buffer sizes can become stale between `GetDisplayConfigBufferSizes` and `QueryDisplayConfig`, that inactive all-path entries lack complete mode data, and that CCD coordinates are physical pixels rather than DPI-virtualized values:

- [QueryDisplayConfig](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-querydisplayconfig)
- [GetDisplayConfigBufferSizes](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getdisplayconfigbuffersizes)
- [DisplayConfigGetDeviceInfo](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-displayconfiggetdeviceinfo)
- [DISPLAYCONFIG_TARGET_DEVICE_NAME](https://learn.microsoft.com/windows/win32/api/wingdi/ns-wingdi-displayconfig_target_device_name)

Target identity starts with the CCD monitor path, friendly name, EDID manufacturer/product fields, connector type, and connector instance. A read-only SetupAPI pass matches the monitor interface path, obtains the device instance ID, and reads EDID from the device registry key. The parser retains normalized identity fields and a short mode signature, not the raw EDID. Native layout tests are based on the installed Windows SDK 10.0.26100 header definitions.

On Windows 11, HDR capture uses documented request type 15 and reads the HDR-supported and HDR-user-enabled bits rather than treating generic Advanced Color activity as HDR. HDR mutation uses request type 16. Older Windows versions that reject those request types fall back to the legacy Advanced Color query and setter. The app treats an unsupported display as HDR off; a failed query is a capture error rather than a partially saved profile. Capture schema 3 records these corrected HDR semantics. Earlier profiles are retained but must be updated from the current setup before activation because their stored generic Advanced Color value cannot be migrated to the user's HDR toggle reliably. Schema 4 additionally captures virtual desktop-image and refresh-boost metadata; schema-3 profiles remain usable, but need recapture to gain those fidelity checks.

### Per-monitor scale compatibility

Windows does not document request types `-3` and `-4`, despite Windows Settings and maintained tools using them. MoniTopo isolates the two packets in `UndocumentedDpiScalePackets.cs`, asserts their 32-byte and 24-byte layouts, runtime-probes every source, and rejects capture when a complete current value cannot be mapped. The percentage table and relative-index mapping were cross-checked on 20 July 2026 against three independent implementations:

- [Firefox `WinUtils.cpp`](https://searchfox.org/firefox-main/source/widget/windows/WinUtils.cpp)
- [MartinGC94/DisplayConfig DPI structures](https://github.com/MartinGC94/DisplayConfig/tree/main/src/DisplayConfig/Native/Structs)
- [lihas/windows-DPI-scaling-sample](https://github.com/lihas/windows-DPI-scaling-sample/blob/master/DPIHelper/DpiHelper.h)

The corresponding setter maps a saved percentage back to the runtime-probed relative index. An unavailable percentage fails preflight; scaling is never silently skipped. Source-specific DPI and target-specific HDR device-info queries are reliable only while that source/target is active; some drivers return `ERROR_GEN_FAILURE` for an inactive target. Preflight queries both capabilities for displays that are already active. For a target that the requested topology will enable, it validates the saved scale against the known Windows steps and defers the exact DPI and HDR checks until after the temporary topology is active. Those checks remain inside the recovery-protected activation transaction and any failure rolls the topology back.

## Activation and recovery

`ProfileActivationService` owns the platform-neutral state machine. It serializes activation, resolves every required identity, captures rollback data, runs capability preflight, validates the complete CCD plan, and starts recovery before the first mutation. It then applies topology temporarily, waits for stable CCD observations, re-resolves addresses, applies scale and HDR, and requires consecutive complete matching captures within a bounded verification interval. Transient display reads restart convergence rather than immediately abandoning a changing desktop. Only verified topology is persisted, followed by another complete verification and `lastActivatedProfileId` update. A failed activation attempts exact rollback with settling, physical-target rebinding, and verification before persistence. Failed exact rollback invokes Windows' extended-topology fallback and verifies that an active source exists; it is reported as fallback, not successful restoration.

`DisplayConfigurationPlanBuilder` reconstructs one source mode per saved source group and one target mode per display. It prefers the source address captured with each group, because a CCD source identifies a rendered desktop surface and arbitrary source swaps can produce a path set that the driver cannot solve. If an adapter address changed, it next prefers the same source ID and finally uses deterministic one-to-one assignment across currently exposed alternatives. It preserves clone groups and refuses legacy/incomplete profiles without a captured target signal.

Supplied paths follow the queried path's virtual-mode capability: advertised virtual paths use packed source/target indices with unused halves set to `0xFFFF`, while other paths use direct indices as documented. Capture remains tolerant of drivers that return packed query indices without the reporting flag. For that contradictory case, activation validates the documented direct representation first and then a packed representation of the same exact modes; only a representation accepted by `SDC_VALIDATE` can proceed to `SDC_APPLY`. Reporting-only path capability flags remain unchanged, dynamic-refresh boost is preserved, and neither validation attempt uses `SDC_ALLOW_CHANGES`. Capture and rollback verification use the validated dual-format resolver described above.

`SetDisplayConfig` is called with `SDC_USE_SUPPLIED_DISPLAY_CONFIG` and either `SDC_VALIDATE` or `SDC_APPLY`. Verified persistence adds `SDC_SAVE_TO_DATABASE`. Virtual-mode and virtual-refresh awareness are always declared; `SDC_ALLOW_CHANGES` is deliberately absent so Windows cannot substitute a nearby mode. The index and path-flag handling follows Microsoft's [source path](https://learn.microsoft.com/windows/win32/api/wingdi/ns-wingdi-displayconfig_path_source_info), [target path](https://learn.microsoft.com/windows/win32/api/wingdi/ns-wingdi-displayconfig_path_target_info), and [path flags](https://learn.microsoft.com/windows/win32/api/wingdi/ns-wingdi-displayconfig_path_info) contracts.

The transient rollback file contains versioned raw CCD paths/modes plus active targets' scale, HDR, and local device-path bindings. Recovery protocol version 2 is independent of profile capture versions. The main process holds an exclusive file lease shared across **all** transactions in the recovery root. The companion also takes a per-transaction lock and completes a readiness handshake before mutation. Every native write checks for requested takeover. At timeout or main-process death, the companion requests ownership and waits for the main lease to be released. If a native call is hung, it can terminate only the original MoniTopo process, verified by PID and creation time, and must confirm its exit and acquire the same lease before writing. It never treats elapsed time alone as permission for competing display writes.

Terminal records distinguish activation success, exact rollback, emergency fallback, unresolved recovery, and abort before mutation. The main process durably publishes its outcome before releasing ownership; publication is irreversible even if acknowledgement fails. It waits for companion acknowledgement/exit before allowing another transaction. Unresolved recovery retains its payload for diagnosis; successful restoration/fallback removes transient rollback data. Startup reads pending `result.json` files, reports the actual outcome, and acknowledges the report without deleting unresolved evidence. Corrupt payloads and failed lease acquisition cannot invoke a display writer. Native reads and recovery exceptions cannot bypass the explicit fallback decision.

The flag combinations and device-info packets follow the current Windows CCD contracts:

- [SetDisplayConfig](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setdisplayconfig)
- [DisplayConfigSetDeviceInfo](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-displayconfigsetdeviceinfo)
- [DISPLAYCONFIG_DEVICE_INFO_TYPE](https://learn.microsoft.com/windows/win32/api/wingdi/ne-wingdi-displayconfig_device_info_type)

## Derived active state and refresh events

Identity resolution produces a deterministic one-to-one map before profile comparison. Active matching then compares the exact active set and every managed property; it never trusts the last button pressed. See [display identity](display-identity.md) for the scoring and alternative-assignment ambiguity check.

Windows display, device, and settings broadcasts reach a hidden top-level message window and feed `DisplayStateRefreshService`; a message-only window would not receive those broadcasts. Bursts are debounced for 350 ms, refreshes are serialized, and a 15-second fallback consistency check covers driver changes that emit no useful message. Polling and pending work are suppressed while the session is locked or the app is shutting down. Shutdown drains active refreshes before disposing their synchronization objects. A changed state becomes `Custom` and updates any visible popup; the refresh service has no activation path.

## Tray lifecycle and input routing

The first process acquires a per-user, per-session named semaphore and listens on a current-user-only named pipe. A later launch writes a newline-framed `open` message, waits for acknowledgement, and exits. The listener reads fragmented frames and enforces a per-client deadline so an incomplete command cannot block later launches. Forwarding failures are reported instead of silently exiting. The primary queues accepted startup requests until the UI is ready and dispatches them to the WPF thread. Tests use a unique application scope so a developer's running instance cannot capture the test pipe or semaphore. Closing the main window hides it; explicit Exit cancels background work, drains interactions/refresh/update operations, and then cleans up UI and IPC resources.

The hidden top-level window owns global hotkeys as well. `GlobalHotkeyService` assigns application-local IDs, always adds `MOD_NOREPEAT`, rejects duplicate MoniTopo bindings before calling Windows, and transactionally restores the previous registration if Windows rejects a replacement. Registration, restoration, and settings rollback always marshal to the HWND-owning UI dispatcher. Re-enable failures are reported rather than ignored. A shared interaction lease excludes conflicting profile edits, settings, and restart/download actions during activation; profile hotkeys are temporarily unregistered while the popup hotkey remains available. See Microsoft's [RegisterHotKey](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-registerhotkey) and [UnregisterHotKey](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-unregisterhotkey) contracts.

The WinForms `NotifyIcon` is limited to tray ownership, its compact context menu, tooltip, and short direct-hotkey notifications. Popup-originated activation reports through inline events and deliberately suppresses the redundant balloon. The tray, main window, and executable share the embedded multi-resolution `Assets/MoniTopo.ico`, generated deterministically by `eng/Generate-AppIcon.ps1` from the offset-monitor geometry retained in `Assets/tray-icon.svg`. WPF loads the icon per window/thread because the ICO decoder remains dispatcher-owned even when a frame is frozen.

The popup presents profiles in saved order as a compact quick-access grid, reducing columns for narrow work areas. Each tile scales the saved monitor positions and resolutions uniformly into a small schematic, staggers clone members, and labels only the profile name and hotkey. Neutral Fluent resources explicitly set the foreground of selected items so system selection colors cannot obscure the text. A check mark identifies the active profile. Arrow/Enter profile handling applies only while the list has keyboard focus, so footer actions retain their normal behavior. Placement uses the primary monitor's physical work area and DPI, never the pointer location; changing the primary monitor refreshes a visible popup's placement. A single gear action opens the main Profiles page; Settings remains inside that window. Available, downloading, and restart-ready update states occupy a bottom strip alongside a separate Release notes action. The footer shows MoniTopo and the current version.

Global hotkeys may have no modifiers. The capture dialog requires an explicit confirmation for such a key and explains its system-wide effect on typing and shortcuts. Conflict validation and `MOD_NOREPEAT` still apply. The dialog runs inside the interaction lease so typing a profile's shortcut cannot activate it during capture. Escape cancels and Tab navigates the dialog instead of becoming a hotkey.

## Profile management and preview

`ProfileManagementService` is the transaction boundary for profile CRUD. Save and update both use the production read-only capture pipeline, normalize the result, and persist through `ConfigurationSession` and the atomic JSON store. A new capture is compared with existing profiles before insertion; an exact duplicate is returned to the UI so it can offer Update instead. Rename, order, delete, hotkey, and remembered-binding changes are validated as complete candidate configurations before saving.

The main window does not edit display geometry. `DisplayLayoutPreview` maps saved physical-pixel rectangles into an available DIP viewport, preserving relative position and adding a small stack offset for clone members. Each monitor rectangle and its accessible tooltip show resolution, friendly refresh, explicitly labelled Windows scale, HDR, and primary state. Manual identity binding only lists currently connected candidates and therefore cannot bind a physically absent display. Saved window placement is optional state: invalid/zero dimensions fall back to a centered size clamped to a work area, and an unshown window never persists its unmeasured actual dimensions. Initialization smoke tests exercise this path with fake services, not just a view model assigned after construction.

The profile list pairs names with formatted direct hotkeys. Selected-profile edit actions sit below the header and summary, above the preview. Settings persists `ThemePreference` as System (default), Light, or Dark; missing values in older configuration files default to System. Application-level WPF `ThemeMode` applies the saved choice before first-run UI and updates open windows immediately after a successful save. Theme resources are dynamic and do not change the OS preference.

## Startup and updates

The first-run window and the main-window setting share `RunAtLoginService`. It writes one quoted `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` command with `--background`; uninstall removes only MoniTopo's value. Installed builds point at Velopack's root execution stub, which survives replacement of the `current` directory. Portable builds use their current executable and warn that moving it breaks startup. Ordinary launches stay in the tray unless the disabled-by-default show-window preference is enabled. First run and second-instance open requests still show profile management.

`Program.Main` initializes `VelopackApp` before WPF. Velopack's default startup behavior applies an already staged update on the next launch; users can instead choose **Restart now**. `UpdateCoordinator` preserves staged state across checks and retains retry actions after download/restart failures. Its lifetime scheduler waits five seconds, then checks eligibility every 15 minutes: successful checks are limited to once per 24 hours, failed attempts have a one-hour retry backoff. Checks never download. It persists time only after a successful check and translates offline, rate-limit, checksum, lock, and unpackaged-development failures. `VelopackUpdateClient` awaits the actual SDK check because it has no cancellation parameter; detaching it would permit concurrent SDK operations, so shutdown can wait for its network timeout. The release-candidate source includes GitHub prereleases; change it to stable-only before approving the first stable release.

The update feed's `NotesMarkdown` is retained with the available/staged version. Tray and Settings expose a separate Release notes action before download and after staging. A native, scrollable, selectable FlowDocument displays headings and bullets without truncation; absent notes have an explicit fallback. Feed content is rendered as literal text, never executable HTML/XAML, remote images, or automatically opened links. Viewing notes has no download/install path. Packaging includes `CHANGELOG.md` as Velopack release notes.

Every primary process creates a bounded per-run text log below `%LocalAppData%\MoniTopo\logs` and writes a startup record containing display version, package version, installed/development channel, assembly/file version, runtime, OS version, and process architecture. Development and installed builds deliberately use the same directory, while the startup record distinguishes them. Activation failures include the stable error code and, for native setters, the decimal and hexadecimal Win32 error code plus a privacy-safe path/mode summary that omits adapter IDs, target IDs, monitor identities, and names. Each file is capped at 1 MiB and only the newest seven are retained. These logs remain local and are never uploaded automatically.

The Windows interop layer was re-evaluated in August 2026. [Microsoft.Windows.CsWin32](https://github.com/microsoft/CsWin32) is the maintained Microsoft source generator for ABI declarations, but it does not construct, validate, or restore a CCD topology. [WindowsDisplayAPI](https://github.com/falahati/WindowsDisplayAPI) supplies a higher-level .NET model, but its last NuGet release predates current Windows 11 virtual-refresh and HDR contracts and its virtual-index assumptions do not match the driver behavior observed during acceptance testing. MoniTopo therefore retains its small source-generated `LibraryImport` surface and synthetic layout tests instead of adding either dependency; topology semantics remain owned and tested here.
